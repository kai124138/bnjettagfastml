# Plots — what each PNG is (and what it is *not*)

Two families of figures live here:

- **Data / architecture diagnostics** (4 PNGs) — emitted by the training pipeline; identical across runs
  by construction.
- **Results figures** (3 PNGs, `results_*` prefix) — generated *post-hoc* by
  [`../../code/plots/make_results_plots.py`](../../code/plots/make_results_plots.py) from the authoritative
  numbers (val AUCs in [`../RESULTS.md`](../RESULTS.md), measured FPGA resources in
  [`../csynth/`](../csynth/)). These are the publication figures.

## Data / architecture diagnostics

Four **unique** images come out of the training pipeline. They are pulled from the headline run
(`/data/outputs/qk-paper-binary-lr15`), but three of the four are **identical across every run** by
construction — so there is exactly one honest copy of each, not one-per-variant.

| file | what it shows | varies per run? |
| --- | --- | --- |
| `model_architecture.png` | Keras graph of the BitNet transformer: `(10×14)` → `BitLinear` input proj → +pos-emb → **8× `BitTransformerBlock`** @ D=256 → `GlobalAveragePooling1D` → `BitLinear` head (256→256) → `BitLinear` head (256→1). | **No** — architecture is identical across `bitnet`/`vanilla`/`w8a8` *by design* (only the matmul precision changes). One diagram covers all. |
| `data_jet_kinematics.png` | Signal vs background jet-level `pT / η / φ` (input data). | **No** — same input data for every run. |
| `data_particle_kinematics.png` | Signal vs background per-constituent `dz / dx / dy / pT / η / φ` (input data). | **No** — same input data for every run. |
| `sample_pt_reweighting.png` | **Per-event *sample weights*, NOT network weights.** Histogram of the flat-`pT` reweighting factor (`qkerasModel.py` ~L627–651: signal events → weight `1.0`; background → `sig_counts/bkg_counts` per `pT` bin). A **data-prep diagnostic**. | **No** — derived purely from the data's `pT` spectrum, independent of model/training. |

## Results figures (the publication plots)

Generated by [`../../code/plots/make_results_plots.py`](../../code/plots/make_results_plots.py) (matplotlib;
run with the project's `.venv-plots` env: `.venv-plots/bin/python code/plots/make_results_plots.py`). Every
number is **sourced, not invented**: val AUCs from `../RESULTS.md` §1; FPGA resources read live at run time
from the measured Vitis csynth reports `../csynth/csynth_report_a{8,6,4}_rf256.json`.

| file | what it shows | source |

| `results_auc_by_variant.png` | Val AUC across all five precisions — vanilla FP32 `0.7703`, W8A8 `0.7719`, **1-bit BitNet `0.7530`** (highlighted = the deployed model), ternary `0.7685`, softmax-free `0.7562` — with the **−1.7 pt** cost of going binary vs FP32 annotated. | RESULTS.md §1a / §1c |

## Honest caveats

1. **`sample_pt_reweighting.png` is easy to misread.** The upstream file is literally named
   `*_weights.png` and its x-axis says "Weights," but it is the *training sample-weight* array (the
   pT-balancing factor), **not** a histogram of the model's learned weights. A true binary-weight
   histogram would be two spikes at ±1; this is the pT-reweighting distribution (spike at 1.0 for all
   signal, a tail for background). Renamed here to prevent that confusion.
2. **Still no ROC-curve or training-curve PNGs.** `ROC.py` was not run inside the training jobs, so no ROC
   image exists on the PVC; the **ROC curves and learning curves live in Weights & Biases** (entity
   `kayamaguchi-uc-san-diego`, project `bnjettag-bitnet`) and each run's `train.log`. The new `results_*`
   figures plot the *scalar* AUCs and the firmware resources — **not** the full ROC sweep. (To add real ROC
   PNGs we would pull per-run `fpr/tpr` from W&B, or re-evaluate the saved `.h5` on the test set.)
3. **`results_auc_by_variant.png` has a truncated y-axis** (0.735–0.776) so the ~1–2 pt AUC gaps are
   legible; the exact AUC is printed on every bar, so nothing is hidden.
